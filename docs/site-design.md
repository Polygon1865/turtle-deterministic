# 每日站点设计方案

> 目标：在“纯静态 HTML + Caddy + Cloudflare Access”的约束下，让每天
> **100 个 A 股候选**、**20 份 A 股报告**和 **20 份港股观察报告**都能被快速浏览、筛选和阅读，而不是把 100 只股票
> 都做成完整报告，也不是只展示 20 行摘要。

## 0. 实现状态（2026-10-22）

方案 C 的 Phase 0 和 Phase 1 主体已落地：

- 首页：今日概览、报告数/QA 统计、优先看 3 张卡片、20 份 A 股 + 20 份港股报告表、100 候选表；
- 候选表：搜索、通道筛选、只看深度、按排名/安全边际/ROE 排序；
- 报告表：行业、研究模式、覆盖率、安全边际、报告链接；
- 报告卡片：从 `snapshot/metrics.json`、`inputs.json`、`research.json` 提取
  综合底价/当前价/安全边际/行业/首条研究结论；
- 发布：`site/releases/<date>/` + `site/current`，发布失败保留旧版；历史 release
  不会被删除，首页/每日页共享日期 tab；
- 历史：扫描 `site/releases/*`，为每个日期生成 `day/<date>/index.html`，报告与
  ranking CSV 复制到 `archive/<date>/`；根 `index.html` 始终展示最新日期；
- 港股：报告表/卡片显示 A/HK 市场标记，港股观察清单与 A 股候选池分开呈现；
- 报告页：Markdown→HTML 渲染器加入统一导航、目录、市场/代码徽章、响应式和打印样式。

尚未完成：站点 `site.json`（当前使用 `site_data.json`）、自选/笔记、报告页
上一只/下一只导航；索引页是单文件静态 HTML（数据内联），无后端依赖。

## 1. 升级前实现审计

当前 `src/turtlefw/site.py` + `site_index.html.j2` 是一个能用的最小站点：

- 首页只有一张表，列：`# / 代码 / 名称 / QA / 研究 / 覆盖率 / 报告`；
- 只展示 `status.json` 里的 20 只报告，**不展示 100 只候选**；
- 没有行业、评分、估值、研究摘要、筛选、搜索、排序、历史归档；
- 个股页直接复制 `analysis_report.html`，没有统一导航；
- 发布采用 `site/releases/<date>/` + `site/current` junction，失败保留旧版，这一点应保留。

结论：发布机制合格，信息架构不足。当前页面回答“今天哪 20 只有报告”，
没有回答“今天从全市场筛出的 100 只是什么、为什么是它们、哪几只值得先看”。

## 2. 调研结论

参考方向（只借鉴原则，不照搬视觉）：

- 财富管理/投资门户通常按“总览 → 组合/标的 → 详情”分层，首页只放决策所需摘要，
  细节下沉到详情页；角色不同，首页信息密度不同。[Devexperts 案例](https://devexperts.com/case-studies/designing-a-wealth-management-platform-investor-advisor-portals/)
- 金融数据仪表盘的关键不是堆图表，而是层级、可比性和可扫描性；表格、筛选、
  一致的数值格式比装饰性图表更重要。[Highcharts + Morningstar 仪表盘实践](https://www.highcharts.com/blog/tutorials/saas-analytics-dashboards-with-highcharts-and-morningstar/)
- 金融界面适合高 x-height、清晰数字字形的字体，并启用 tabular numerals，
  让表格数字对齐。[Fonts in Financial Services](https://www.gate39media.com/blog/design-spotlight-fonts-in-financial-services)

对本地场景的推论：

1. **首页是“日报封面 + 候选池”，不是报告仓库。** 30 份报告是深度内容，
   100 只候选是扫描内容，两者信息层级不同。
2. **先结论，后证据。** 首屏先回答“今天有多少报告、QA 是否可信、哪几只排前面”；
   再给候选表和报告列表。
3. **静态站点足够。** 100 行数据不需要后端；搜索/筛选/排序用少量原生 JS 即可，
   无 JS 时仍应能读完整个表。
4. **不要做“实时行情终端”。** 数据是收盘后日更，界面应明确“数据日”，
   不应伪装成实时行情。

## 3. 三个方向

| 方向 | 首页形态 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| A. 研究报告库 | 20 张报告卡片 + 简单列表 | 实现最快、阅读舒服 | 100 只候选无处安放，扫描效率低 | 只看少量报告 |
| B. 研究终端 | 密集表格 + 筛选器 + 侧栏 | 扫描 100 只效率最高 | 首屏压迫、手机体验差、开发量大 | 专业日盯盘 |
| C. 日报封面 + 研究终端（推荐） | 上半屏日报摘要/40 份报告，下半屏 100 候选表 | 兼顾“先看结论”和“全量扫描”；可渐进实现 | 需要明确层级，避免首页过长 | 个人每日复盘 |

推荐 **C：Daily Research Terminal**。视觉上偏编辑型（Editorial），
交互上偏终端型（Terminal）：首屏可读，候选表可扫。

## 4. 推荐信息架构

```text
/                         最新日日报（封面 + 报告 + 100 候选）
/day/<date>/index.html    历史日日报
/archive/<date>/...       历史日的报告与 ranking CSV
/report/<code>.html       单票报告（统一导航/目录）
/ranking.csv              100 只 fast 候选
/ranking_deep.csv         20 只 deep 候选
```

### 4.2 个股报告页

报告 HTML 已加入统一外壳：顶部品牌/返回入口、代码/市场徽章、数据口径提示；
左侧可折叠目录（h2/h3）、右侧正文；表格横向滚动、移动端单栏、打印时隐藏目录。
正文数字与 Markdown 源保持一一对应，渲染器不重算任何指标。上一只/下一只导航
尚未实现。

## 5. 页面字段

### 5.1 候选池（100 只）

来自 `ranking.csv`，建议字段：

| 字段 | 来源 | 说明 |
|---|---|---|
| `rank` | 行序 | 快速筛选排名 |
| `code/name` | ranking | 代码、名称 |
| `channel` | ranking | 主通道/观察通道 |
| `roe` | ranking | ROE |
| `payout` | ranking | 派息率 |
| `r` | ranking | R |
| `gg` | ranking | GG |
| `ii` | ranking | II |
| `margin` | ranking | 安全边际/排序键 |
| `verdict` | ranking_deep | 深度分析结论；失败行要显式标记 |

### 5.2 今日报告（20 只）

来自 `status.json` + `snapshot/manifest.json` + `metrics.json`，建议字段：

- 现有：代码、名称、排名、QA、研究模式、覆盖率、报告链接；
- 新增：行业、综合底价/当前价/安全边际、核心结论（研究文档第一条 claim 或报告摘要）、
  数据日、PDF 是否有索引；
- 研究失败时显示“确定性回退”，不要伪装成 LLM 研究。

### 5.3 站点元数据

建议生成 `site.json`（或 `index.json`），包含：

```json
{
  "date": "2026-10-22",
  "trade_date": "20261021",
  "generated_at": "2026-10-22T19:12:00",
  "candidate_count": 100,
  "report_count": 20,
  "qa_pass": 20,
  "reports": [],
  "candidates": []
}
```

好处：页面渲染、历史归档、外部检查共用一份数据；也方便未来做 API/静态搜索。

## 6. 视觉与交互

- **布局**：最大宽度 1200–1280px；桌面双栏（报告卡片 2 列），手机单列。
- **颜色**：米白/深墨为主；一个蓝色强调链接；绿色只表示 QA PASS，红色只表示失败/风险；
  不用红绿表示涨跌（没有实时行情）。
- **字体**：中文系统字体栈；数字启用 `font-variant-numeric: tabular-nums`；
  正文 15–16px，表格 13–14px。
- **密度**：首屏不超过 3 个信息块；候选表默认 25 行，提供“显示全部”。
- **交互**：原生 JS 做搜索/筛选/排序；URL query 保存筛选状态；
  无 JS 时保留完整表格和报告链接。
- **可访问性**：表格有 caption/scope；颜色不是唯一状态；键盘可操作；对比度达标。
- **性能**：单页 < 200KB（不含报告），无外部字体/JS 依赖；100 行直接内联。

## 7. 实施顺序

### Phase 0（先做，1 天内）

1. `build_site` 发布 `ranking.csv` / `ranking_deep.csv`（已支持）；
2. 首页拆成“今日 40 份报告”和“候选池 100”两个区块；
3. 候选表加搜索、通道筛选、排序；
4. 报告列表加行业/研究模式/覆盖率；
5. 保留现有 QA 状态与发布机制。

### Phase 1（2–3 天）

1. 从 `metrics.json` 提取估值/安全边际/核心指标，生成报告卡片摘要；
2. 今日概览与“优先看”3 张卡片；
3. 历史归档页；
4. 报告页统一导航外壳。

### Phase 2（可选）

1. 候选池与报告页联动（点击候选跳到报告，无报告则显示“未深度分析”）；
2. 图表（已有 SVG 图表能力，可复用）；
3. 自选/笔记（需要本地存储或后端，先不做）。

## 8. 不做的事

- 不做实时行情/分钟线；数据是日更。
- 不把 100 只都生成完整报告；深度报告只给前 20。
- 不引入 React/Vue/数据库；静态 HTML + 少量原生 JS 足够。
- 不在浏览器存 API key；所有数据在构建时生成。
- 不用颜色暗示买卖建议；页面只展示事实、估值区间和 QA 状态。

## 9. 验收标准

- 首页在手机和桌面都能在 5 秒内回答：数据日、报告数、QA 是否通过、前 3 只；
- 100 只候选可搜索/筛选/排序，滚动不卡；
- 40 份报告都能从首页一键打开；
- 无 JS 时仍可看到完整报告列表和候选表；
- 发布失败时 `site/current` 仍指向上一版；
- 首页不出现报告正文中的数字，除非来自同一份 `metrics/data_pack` 数据源。
